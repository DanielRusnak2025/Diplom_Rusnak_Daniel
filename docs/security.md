# Безопасность NewsDove

## JWT-аутентификация

**Алгоритм:** HMAC256  
**Issuer:** `newsdove`  
**TTL access-токена:** 15 минут (`accessTokenTtlMs = 15 * 60 * 1000`)  
**Содержимое:** `sub` = userId (строка), `role` = строковое представление роли  
**Секрет:** минимум 32 байта; передаётся через `jwt.secret` в `server.properties` или переменную окружения `NEWSDOVE_JWT_SECRET`. Сервер не стартует, если секрет отсутствует или короче 32 байт.

Секрет **никогда** не сохраняется в git и не выводится в логи.

---

## Refresh-токены

**TTL:** 30 дней  
**Генерация:** 32 случайных байта, закодированных в Base64 URL без паддинга  
**Хранение:** в базе хранится SHA-256 хэш токена (`token_hash`); raw-значение на сервере не сохраняется  
**Ротация семейства:**
- Каждый refresh-токен принадлежит `family_id` (UUID)
- При обновлении (`/auth/refresh`) старый токен помечается как отозванный, выдаётся новый с тем же `family_id`
- Если клиент пытается использовать уже отозванный токен (кража / повтор) — сервер отзывает **всё семейство** и возвращает `403 TOKEN_REUSED`

## Защита входа (LoginProtection)

Механизм защиты от брутфорса на уровне приложения:

**Алгоритм задержки (экспоненциальный backoff):**

```
delay = min(2^(attempt-1) * 1000 мс, 60 000 мс)
```

Примеры: попытка 1 → 1 с, 2 → 2 с, 3 → 4 с, 4 → 8 с, 5 → 16 с, 6 → 32 с, 7+ → 60 с

**Хранение:** `ConcurrentHashMap` в памяти; максимум 10 000 записей  
**Окно сброса:** 15 минут (`EVICT_AFTER_MS = 15 * 60 * 1000`)  
**Ключ:** login (ник) пользователя

При превышении порога сервер возвращает `429 TOO_MANY_ATTEMPTS` с информацией о времени ожидания.

## Хеширование паролей

**Алгоритм:** Argon2**id** (вариант RFC 9106; `Argon2Factory.Argon2Types.ARGON2id`) — библиотека `argon2-jvm` v2.12  
**Класс:** `org.example.security.PasswordHasher` (строка 17)  
**Параметры:** iterations=3, memory=64 MiB (65 536 KiB), parallelism=4; максимальная длина пароля 128 символов

Пароли **никогда** не передаются в открытом виде: ни в логах, ни в API-ответах, ни в тестах.

## Роли и авторизация

Роли хранятся в колонке `user.role` (VARCHAR):

| Роль | Права |
|------|-------|
| `USER` | Доступ к ленте, настройкам, профилю, оценкам, жалобам |
| `MODERATOR` | Всё как USER + просмотр жалоб и статей в админ-панели, скрытие статей |
| `ADMIN` | Всё как MODERATOR + управление пользователями, аудит, статистика, смена ролей |

RBAC проверяется **на сервере** при каждом запросе. Android-приложение использует роль для навигации, но сервер не доверяет клиенту.

Назначение роли ADMIN через CLI: `./gradlew :core:run --args="--make-admin <ник>"`

## Журнал аудита

Таблица `audit_log` фиксирует административные действия:

- `user_id` — кто совершил действие
- `action` — тип действия (например, `HIDE_ARTICLE`, `CHANGE_ROLE`)
- `target_kind`, `target_id` — над каким объектом
- `created_at` — временная метка

Доступен через `GET /api/v1/admin/audit` (только `ADMIN`).

## HTTPS и TLS

**Схема:** самоподписанный CA для локальной сети  
**Порт HTTPS:** 8443  
**Порт HTTP:** 8080 (только `/health`; все `/api/*` возвращают `403 HTTPS_REQUIRED` по HTTP)  
**Keystore:** PKCS12, путь вне репозитория (`C:\newsdove_tls\`)  
**Пароль keystore:** только через переменную окружения `NEWSDOVE_KEYSTORE_PASSWORD`

Подробная инструкция по генерации: [docs/tls-setup.md](tls-setup.md)

**SAN сертификата:** `IP:<LAN_IP>`, `IP:10.0.2.2` (Android-эмулятор), `DNS:localhost`

---

## Доверие CA в Android

Android-приложение доверяет только:
1. Системным сертификатам (стандартный набор Android)
2. Сертификату локального CA (`ca.crt`, встроен в APK как `res/raw/newsdove_ca.crt`)

Настраивается через `network_security_config.xml`. Пользовательские/системные CA для `newsdove` не требуются — CA встроен в APK.

---

## Android Keystore

Access- и refresh-токены хранятся в зашифрованном виде с помощью Android Keystore:

- Ключ шифрования создаётся и хранится в Android Keystore (не экспортируется)
- Данные сохраняются в `EncryptedSharedPreferences` / DataStore (`tokenRepository`)
- Даже при получении файла хранилища без ключа данные недоступны

Данные админ-панели **не кешируются** в Room или других локальных хранилищах.

---

## Что никогда не попадает в git или логи

- Пароль базы данных
- Gmail app-password
- JWT signing secret
- TLS private keys и пароль keystore
- Argon2-хэши паролей пользователей
- Raw refresh-токены
